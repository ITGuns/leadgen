- **D17 · two-phase website filter:** at pull time the `has website` filter uses the *static* classification (none/social_only/aggregator are known offline; real-vs-parked/dead needs a fetch). Candidates enter the pipeline, the website_check stage classifies them, and the score stage detaches leads that then violate the campaign's filter — reported as "filtered post-classification". This is what makes "no website" campaigns able to find parked/dead-site leads at all.
- **D18 · Taxonomy derived from release data (2026-09-07):** the canonical Overture category CSV is gone from the OvertureMaps/schema repo, so `data/overture_taxonomy.csv` (1,792 codes) is now DERIVED from the pinned release itself via `scripts/derive-taxonomy.ts` (DISTINCT taxonomy + hierarchy over DE/NV/CT, provenance in `data/.taxonomy-derivation.json`). Niche mappings, mock fixtures, and the G2 golden set were reconciled to the real vocabulary (e.g. `roofing` not `roofing_contractor`, `plumbing` not `plumber`). Verified: a REAL Delaware ingest gates at 0.00% unresolved taxonomy. Re-derive when bumping releases; a rarely-seen category from an unscanned state would surface in the gate report exactly as designed.

- **D19 · Vercel + Supabase deployment (2026-09-07, user-directed):** the app now targets Vercel (serverless) with Supabase Postgres, keeping local/Docker fully working. One Postgres schema (`src/db/schema.ts`, pg-core), two drivers behind `initDb()`: `DATABASE_URL` set → postgres-js against the Supabase **transaction pooler** (`prepare:false`, pool max 1 on Vercel); unset → **PGlite** (in-process WASM Postgres) under `PGLITE_DIR` — keyless dev/CI/Docker need zero accounts, and better-sqlite3 is gone. Migrations run at init; racing cold starts resolve via migrator idempotence + one delayed retry (an advisory lock proved UNUSABLE through the transaction pooler — session-scoped lock/unlock land on different pooled connections and the lock never releases, hanging all later boots; hit live on first deploy). Jobs: the persisted `jobs` table stays the queue in both runtimes; on Vercel there is no resident worker — Vercel Cron (`vercel.json`, every minute) hits `/api/jobs/tick` (Bearer `CRON_SECRET`, `maxDuration=300`) which runs `Worker.runSlice(JOB_SLICE_MS)`; handlers got a `deadline` in JobContext and a deadline-stop requeues **without burning an attempt**, so checkpoint-resumable jobs continue across ticks; enqueue routes also kick a short `after()` slice so work starts without waiting for cron; stale-heartbeat (10 min) recovery replaces boot-time recover. Export artifacts: `/tmp` is per-invocation, so with `SUPABASE_URL`+`SUPABASE_SERVICE_ROLE_KEY` set the finished file uploads to the private Supabase Storage bucket `exports` (`exports.path` = `supabase:<object>`; download route redirects to a short-lived signed URL) — local keeps the exports dir. The DuckDB monthly extract **never runs on serverless** (native module, excluded from tracing): run `DATABASE_URL=<supabase> npx tsx scripts/workstation-extract.ts <STATES>` from any machine — it writes straight into Supabase.
- **D20 · `AUTH_TRUST_PLATFORM` (explicit auth weakening switch):** default auth stays CF-Access-JWT fail-closed (G8). Setting `AUTH_TRUST_PLATFORM=1` (+ `OPERATOR_EMAIL`) makes proxy + `getIdentity` trust the platform's own door instead — for Vercel Deployment Protection, where requests carry no CF JWT. Never enable it on a deployment whose URL is publicly reachable without platform auth.
- **D21 · Backups are Supabase-managed on the shared DB:** the nightly backup job self-skips with a visible reason when `DATABASE_URL` is set (Supabase runs daily backups/PITR; a function can't stream a reliable dump) — verify in the Supabase dashboard. Local PGlite keeps real backups: tar+gzip of the data dir, 30-day retention, Drive push when connected. D8 revised: the encrypted secret store moved from `CONFIG_DIR` files to the `secure_config` table (same AES-256-GCM under `APP_SECRET`) because serverless has no volume.
- **D22 · Supabase driver is node-postgres, not postgres-js (2026-09-09, found live):** postgres-js wedges PERMANENTLY when 3+ zero-parameter queries (exactly what drizzle's `count(*)` selects compile to) run concurrently on a shared connection through the Supavisor transaction pooler — reproduced with prepare on AND off, max:1 and mixed; parameterized queries were unaffected, which is why it survived every earlier test. `pg` checks a connection out per query and never interleaves. Also from the same incident: functions are pinned to `sin1` (`vercel.json` regions) to co-locate with the DB — /api/settings went 9.3s → 0.3s; `initDb`/`boot` clear their cached promise on rejection so one transient cold-start failure can't poison a warm instance; and on Hobby (daily crons only) `kickJobsAfterResponse` keeps slicing up to ~4 min after a response until the queue is empty, which is what actually drives queued jobs to completion there.
- **D23 · `APP_PASSWORD` login (2026-09-10):** Vercel's Standard Protection guards deployment/preview URLs but NOT the production domain (verified live: prod 200, deployment URLs 302), and production-domain protection is a paid add-on. Real mode therefore ships its own front door: setting `APP_PASSWORD` makes the proxy demand HTTP Basic (any username, constant-time compare, browser prompt) on every non-public path, and `getIdentity` re-verifies the same header for API routes (defense in depth, G8). A configured password is ALWAYS required — it takes precedence over `AUTH_TRUST_PLATFORM`. CF Access (the original design) remains the strongest option when configured.
